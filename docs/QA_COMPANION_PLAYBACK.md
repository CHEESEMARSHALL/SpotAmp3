# Companion Playback QA Gate

SpotAmp product music playback is validated through the paired desktop SpotCore companion. A local WAV fixture, direct Plex endpoint, or Media3 service smoke test is not an end-to-end product playback result.

## Automated real-companion tier

The dedicated `companion` tier drives the current SpotCore Qt `CompanionHttpServer` through the QA-only `CompanionQaServer.exe` built from `native-qt`. It does not import or fall back to the legacy Electron `CompanionServer.js`. Run it with:

```powershell
.\scripts\qa.ps1 companion
```

The runner discovers the adjacent `..\SpotCore` checkout by default; call `scripts\qa-companion-real.ps1 -SpotCoreRoot <path>` when it is elsewhere. It starts the Qt QA server against an isolated SQLite database and disposable generated audio/artwork/lyrics fixtures, forwards only the dedicated loopback ports with `adb reverse`, and supplies the exact one-time pairing payload generated by Qt to the Android instrumentation. The Android journey exercises the production pairing parser/claim, library sync, artwork and lyrics fetches, analysis and playlist sync, companion streaming, offline playback/download recovery, event-outbox retry, and other contract paths. Checkpoints and sanitized reports are saved under `qa-results\companion-runs\<run-id>`; the short-lived pairing readiness file is removed after the run.

The gate requires the current Qt QA executable (or a configured Qt build from which it can be built) and an available paired Android test device. If either is unavailable, the explicit companion tier reports `BLOCKED`; it never certifies the legacy Electron server as a substitute. The harness holds a host-wide mutex while using the shared device and QA artifacts, so concurrent runs are rejected until the active run finishes.

The automated journey also downloads one uniquely keyed QA fixture through `MusicRepository.downloadTrack`, switches the app to offline-only mode, and verifies that the downloaded file plays locally and resumes with its position intact. It then removes only that temporary download row/file. Separate checks inject a Qt service outage to validate playback-event outbox retry and canonical history recovery. These automated playback-state checks are Level-B evidence; they do not verify independent audible output.

The same run also seeds a separate uniquely keyed failed-download row, opens the production Downloads destination, taps that row’s Retry button, and observes the real WorkManager download complete against SpotCore with a nonempty local file. It removes and checks the fixture row/file afterward. This verifies the listener-facing action through the production handler and worker—not just handler invocation in isolation.

The normal `quick` and `full` tiers do not depend on SpotCore. A missing adjacent checkout, missing device, or unavailable reverse path produces `BLOCKED` infrastructure evidence for the explicit companion tier.

## Manual audible-observation preconditions

- Use the normal debug APK or the locally signed QA APK for the real companion gate. The QA APK defaults to loopback-only origins, but a scanned QR payload explicitly approves its exact HTTPS companion origin for the current session, including a controlled Cloudflare tunnel. Never use a production credential in a fixture or test report.
- Start the desktop SpotCore companion with a disposable library containing at least two playable tracks.
- Pair the phone through the normal Add Device QR flow.
- Confirm the phone has a valid companion backend origin, device identity, and device token.
- Record the phone model, Android version, SpotCore build, network topology, and test run ID.

If the desktop companion cannot be paired or is unavailable, mark this gate `BLOCKED`; do not substitute local-file playback and do not report the result as PASS.

## Journey

1. Open the paired library and confirm that the selected track is companion-backed (`companion:` identity and a stream URL on the configured SpotCore origin).
2. Start playback and verify audible audio, a playing notification, elapsed position advancement, and the expected current-track identity.
3. Pause and resume; verify the position does not reset unexpectedly.
4. Seek within the track; verify the player remains on the same track and position changes.
5. Play the second track and verify queue advancement and notification metadata.
6. Stop or background the app, then return and verify playback state restoration against the companion-backed queue.
7. Temporarily interrupt the phone-to-companion connection, then restore it. Record whether the app exposes a clear error/retry state and whether it avoids sending credentials to an unintended origin.
8. Verify the companion playback event is eventually delivered once. If delivery is ambiguous, verify retry uses the same event identity and does not duplicate the server-side event.

## Evidence

Attach the QA report, logcat/playback trace, and a short observation for each journey step. Redact device tokens, backend tokens, QR payloads, and private host addresses before sharing artifacts.

Start from [QA_COMPANION_OBSERVATION_TEMPLATE.json](QA_COMPANION_OBSERVATION_TEMPLATE.json) when recording the manual evidence. Replace the placeholder run/build values, set `redactionConfirmed` to `true` only after review, and keep the template redacted: never add device tokens, backend tokens, QR payloads, or private host addresses.

The automated suite covers the supporting contracts: companion track mapping, exact-origin credential selection, cross-origin redirect stripping, playback state/session lifecycle, event outbox isolation, deterministic local Media3 fixture handling, and a loopback companion stream through the real PlaybackManager/Media3 HTTP path. The explicit `companion` tier adds real SpotCore protocol and Level-B playback evidence when its adjacent source checkout and device are available. Neither automated tier claims physical audible output without this separate observation gate.

`scripts/qa-companion.ps1` assigns each gate invocation a run ID. When run outside the main QA runner, an existing standalone companion report is copied under `qa-results/companion-runs/<run-id>/` before the latest report is replaced. A supplied observation retains its own observation run ID separately from the gate run ID.

## Result vocabulary

- `PASS`: all journey steps were observed with a real paired SpotCore session.
- `BLOCKED`: pairing, companion availability, or required audio observation was unavailable.
- `FAIL`: a journey step contradicted the companion contract or exposed a credential/state defect.
